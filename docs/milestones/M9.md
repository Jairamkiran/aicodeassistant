# Milestone 9 — AI Improvements

**Objective.** Make the AI layer produce *machine-usable* output instead of
prose, and spend that capability on a second real feature: AI code review. Then
make retrieval ranking tunable and measurable.

## Scope decisions (L6 review)

- **Provider-agnostic structured output** (ADR-0015). Ollama and OpenAI expose
  different JSON-mode fields, and committing to either would leak a vendor
  concept into the `ChatModel` port. Instead: a shared JSON instruction appended
  to the prompt plus a **balanced-brace extractor that respects string literals
  and escapes**, so a `}` inside a string cannot truncate the parse. Works
  identically on both providers, no DTO leak, `StructuredOutputException` on
  genuinely unparseable output.
- **No JSON-schema-validation framework**: the extractor plus Jackson binding to
  a private DTO is enough. A schema library would add a dependency to catch
  errors the binding already catches.
- **`codeintel` built on the existing ports**: it consumes `retrieval :: search`,
  `ai :: chat`, and `iam :: api` — no new infrastructure, no new external
  dependency. That is the payoff of the M5–M7 boundaries.
- **Weighted RRF rather than a cross-encoder re-ranker**: tuning two weights is
  free at query time; a re-ranker means another model, another network hop, and
  another failure mode. Revisit only if the evaluation harness shows fusion is
  the bottleneck.
- **Deferred:** cross-encoder re-ranking, PR-diff-aware review, test generation,
  a cost ledger.

## Structured output

```java
// ai :: chat  (public, provider-neutral)
StructuredOutputs.jsonInstruction(...)   // appended to the system prompt
StructuredOutputs.extractJson(raw)       // balanced-scan, string/escape aware
```

The extractor scans for the first balanced JSON object, tracking whether it is
inside a string literal and whether the previous character was an escape. This
is the one piece of parsing subtlety in the milestone, and it is unit-tested
against fenced code blocks, leading prose, and braces inside strings.

## Code review flow

```
POST /api/v1/code-reviews  {organizationId, repositoryId, focus}
        │  (authz: iam OrganizationAccess.canRead)
        ▼
  CodeReviewService
    1. CodeSearch.search(focus, org, repo)            ← M5 retrieval
    2. ReviewPromptBuilder (pure): guardrail-fenced <context> + JSON instruction
    3. ChatModel.chat(...)                            ← M6
    4. StructuredOutputs.extractJson -> private ReviewJson DTO
    5. map to domain: CodeReview{ ReviewFinding(severity, file, line, message) }
```

`ReviewJson` is package-private — the model's wire shape never escapes the
adapter. `ReviewSeverity` is a domain enum, so an unknown severity from the
model is rejected rather than propagated.

## Retrieval ranking

- `ReciprocalRankFusion.fuseWeighted(WeightedList...)` — per-retriever weights,
  configurable via `aicodeassistant.retrieval` (`rrf-k`, `vector-weight`,
  `lexical-weight`). Still a pure function.
- `RankingEvaluationTest` — a deterministic harness computing **recall@k** and
  **MRR** over fixed fixtures, so a ranking change is a measurable regression,
  not a vibe.

## Testing strategy

- **Executed, no Docker:** `StructuredOutputsTest` (fenced blocks, prose
  preamble, braces inside strings, malformed → exception);
  `ReviewPromptBuilderTest` (guardrail present, context fencing, JSON
  instruction); `CodeReviewServiceTest` (fake search + chat: findings mapped,
  org scoping, unparseable model output surfaces cleanly);
  `RankingEvaluationTest` (recall@k + MRR); `ModularityTests.verify()`.
- **Manual/live:** review quality against a real model — prompt, parsing, and
  mapping are all verified with fakes.
