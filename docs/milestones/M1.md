# Milestone 1 — Identity & Access

**Objective.** Real authentication and authorization: registration, login, JWT
access tokens + rotating refresh-token families (with reuse detection), users,
organizations, memberships, and role-based access control — built as the first
fully hexagonal bounded context.

## Architecture

The `iam` module realises the target architecture from
[`ARCHITECTURE.md` §1a](../ARCHITECTURE.md): a pure domain, an application layer
of use cases, and adapters on the edges.

```
iam/
├── domain/                     # pure Java — no Spring/JPA/servlet
│   ├── model/                  # User, Organization, Membership, RefreshToken,
│   │                           #   Email, Role, typed ids (aggregates + VOs)
│   ├── event/                  # UserRegistered, OrganizationCreated
│   ├── port/                   # UserRepository, OrganizationRepository,
│   │                           #   MembershipRepository, RefreshTokenStore,
│   │                           #   PasswordHasher, AccessTokenIssuer,
│   │                           #   RefreshTokenGenerator  (interfaces)
│   └── <exceptions>            # EmailAlreadyRegistered, InvalidCredentials, ...
├── application/                # use cases (@Service, @Transactional)
│   ├── RegisterUserService     # register + publish UserRegistered
│   ├── AuthenticationService   # login → issue tokens
│   ├── TokenService            # issue / rotate / revoke + reuse detection
│   ├── TokenFamilyRevoker      # REQUIRES_NEW family revocation (see below)
│   ├── OrganizationService     # create org, add member (RBAC-checked)
│   └── UserQueryService        # read-side (/me)
├── adapter/
│   ├── persistence/            # JPA entities, Spring Data repos, port impls, mapper
│   ├── security/               # BCrypt hasher, JWT issuer, SecureRandom refresh gen,
│   │                           #   Spring Security filter chain
│   └── rest/                   # AuthController, UserController, OrganizationController,
│   │                           #   DTOs, HttpOnly refresh-cookie factory
└── config/                     # IamAuthProperties (typed config)
```

Dependency direction points inward: `adapter → application → domain`. The
domain defines ports; adapters implement them (Dependency Inversion). Nothing in
`domain` imports Spring, JPA, or servlet types.

## Authentication flow (login + rotation)

```
Client                AuthController      AuthenticationService   TokenService        Postgres
  │  POST /login          │                     │                    │                  │
  ├──────────────────────►│                     │                    │                  │
  │                       ├── login(cmd) ───────►│                    │                  │
  │                       │                      ├── verify password  │                  │
  │                       │                      │   (BCrypt)         │                  │
  │                       │                      ├── issueForNewSession(user) ──────────►│
  │                       │                      │                    ├── save RT (family, hash) ►│
  │                       │◄──── AuthenticationResult (access JWT + raw refresh) ────────┤
  │  200 + Set-Cookie:    │                      │                    │                  │
  │  refresh (HttpOnly)   │                      │                    │                  │
  │◄──────────────────────┤                      │                    │                  │
  │                       │                      │                    │                  │
  │  POST /refresh (cookie)│                     │                    │                  │
  ├──────────────────────►├── rotate(raw) ───────────────────────────►│                  │
  │                       │                      │   hash → lookup ───────────────────────►│
  │                       │                      │   if used/revoked → revokeFamilyNow() (REQUIRES_NEW) → 401
  │                       │                      │   else markUsed + issue successor ─────►│
  │◄─── 200 + new access + rotated refresh cookie ────────────────────┤                  │
```

### Refresh-token reuse detection (security-critical)

Each login opens a token **family**. Rotation consumes the presented token and
issues a successor in the same family. If an **already-used or revoked** token is
presented again (a replay of a stolen secret), the **entire family is revoked**
and the request is refused.

The revocation runs in a **`REQUIRES_NEW` transaction** (`TokenFamilyRevoker`)
because the surrounding `rotate()` then throws to reject the request — a single
transaction would roll the revocation back. This was caught by the
`refreshTokenReuseIsDetectedAndFamilyRevoked` end-to-end test, which failed until
the propagation was corrected. Tokens are stored only as **SHA-256 hashes** of
256-bit random secrets; passwords as **BCrypt** (strength-12, delegating encoder
so the scheme is upgradable).

## Database schema (Flyway `V2__iam.sql`)

| Table | Purpose | Notable constraints |
| --- | --- | --- |
| `users` | credentials + profile | unique `email`, unique `lower(email)`, status check |
| `organizations` | tenants | unique `slug` |
| `memberships` | user↔org with role | unique `(user_id, organization_id)`, role check, FKs cascade |
| `refresh_tokens` | rotation families | unique `token_hash`, family/user indexes, partial active index |

## API

| Method | Path | Auth | Description |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/register` | public | Register; returns user id (201) |
| POST | `/api/v1/auth/login` | public | Login; access token (body) + refresh (HttpOnly cookie) |
| POST | `/api/v1/auth/refresh` | cookie | Rotate tokens |
| POST | `/api/v1/auth/logout` | cookie | Revoke family, clear cookie (204) |
| GET | `/api/v1/users/me` | bearer | Current user + memberships |
| POST | `/api/v1/organizations` | bearer | Create org (creator becomes OWNER) |
| POST | `/api/v1/organizations/{id}/members` | bearer + ADMIN | Add/re-role a member |

All errors use the RFC-9457 problem-detail format from `platform-web`.

## Design decisions & trade-offs

- **Refresh delivery = HttpOnly cookie** (access token in body). Mitigates XSS
  token theft; `SameSite=Strict` mitigates CSRF; path-scoped to `/api/v1/auth`.
- **Refresh store = Postgres** (not Redis) in M1 — durable, auditable, one infra
  dependency. Abstracted behind `RefreshTokenStore`; Redis arrives in M2.
- **JWT = HMAC HS256** with a config secret — simplest credible choice for a
  single service. Asymmetric (RS256) keys are a later option if tokens must be
  verified by other services.
- **Org RBAC checked in the application service** (membership lookup) rather than
  baked into the token, so role changes take effect immediately without waiting
  for token expiry.
- **Known limitation:** the login unknown-email path has a minor timing
  side-channel (no hash comparison performed). Documented; a dummy-hash compare
  is a future hardening step.

## Testing strategy

- **Domain unit tests** (no Spring): value objects, `Role` hierarchy,
  `RefreshToken` rotation/expiry/idempotency.
- **End-to-end (H2, no Docker):** `AuthFlowE2eTest` drives the real HTTP stack
  through the Spring Security filter chain — register → login → `/me` → refresh →
  logout, plus 401/409/reuse-detection negative paths.
- **Integration (Testcontainers Postgres, CI):** `IamPersistenceIT` validates the
  JPA mappings and family revocation against real Postgres types.
