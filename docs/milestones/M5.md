# Milestone 5 — Retrieval (Hybrid Search)

**Objective.** Make the vectors written in M4 searchable: hybrid **vector +
lexical** search over `code_chunks`, fused with reciprocal-rank fusion, returning
ranked hits with **file:line provenance**, org-scoped, via a REST endpoint. This
is the retrieval half of RAG; the chat generation is M7.

## Scope decisions (L6 review)

- **Lexical backend → Postgres FTS, not OpenSearch** (ADR-0011): the chunks
  already live in Postgres, so FTS adds lexical search with **zero new
  infrastructure and no dual-write**. OpenSearch deferred until relevance/scale
  demands it.
- **Eval → lightweight fusion-correctness test**, not a full recall@k corpus:
  proves "hybrid > vector-only" deterministically without an arbitrary corpus.
- **Deferred:** cross-encoder re-ranking (until eval shows fusion insufficient)
  and token-budgeted context assembly (→ M7, where the prompt/token budget live).

## How hybrid search works

```
POST /api/v1/search {organizationId, repositoryId?, query, limit}
        │  (authorize: iam OrganizationAccess.canRead)
        ▼
   HybridCodeSearch
        ├── embed(query) ──▶ EmbeddingClient (Ollama)  ── unavailable? ─▶ lexical-only
        ├── VectorSearchDao:  ORDER BY embedding <=> query::vector   (pgvector KNN, HNSW)
        ├── LexicalSearchDao: content_fts @@ plainto_tsquery, ts_rank (Postgres FTS, GIN)
        ▼
   ReciprocalRankFusion.fuse(vectorRanks, lexicalRanks)   score = Σ 1/(k+rank)
        ▼
   top-N SearchResult (file:line provenance, source VECTOR/LEXICAL/HYBRID)
```

**Why hybrid:** vector search captures intent/paraphrase; lexical captures exact
identifiers, error strings, and rare symbols — exactly what code search needs.
RRF fuses the two rank lists using only rank position, so the retrievers'
incomparable raw scores need no normalisation. A chunk found by *both* retrievers
is marked `HYBRID` and rises to the top. If embeddings are unavailable, search
degrades gracefully to lexical-only (availability over completeness on a read
path).

## Module design

- **`retrieval`** gains the `search` named interface (`CodeSearch`,
  `SearchQuery`, `SearchResult`) beside the M4 `chunk` write interface. The
  vector/lexical DAOs, RRF, and `HybridCodeSearch` are internal. Depends on
  `ai :: embedding` (embed the query) and `iam :: api` (org-scoped auth) —
  explicit allowed dependencies, modularity-verified.
- **`RRF`** is pure logic (no I/O) — fully unit-tested, reusable.
- The **worker** scans only `retrieval.chunk` (write side), not `retrieval.search`
  — a headless worker must not wire the search REST controller (caught by the
  worker context test).

## Database schema

- `V9__code_chunks_fts.sql` — adds a **generated** `content_fts tsvector` column
  (`to_tsvector('english', content)`, STORED) + GIN index. Additive, no backfill
  (Postgres maintains it automatically).

## API

| Method | Path | Description |
| --- | --- | --- |
| POST | `/api/v1/search` | Hybrid search; body `{organizationId, repositoryId?, query, limit}`; returns hits with file:line provenance. Requires read access to the org. |

## Testing strategy

- **Executed, no Docker (9 tests):**
  - `ReciprocalRankFusionTest` — ranking math, dedup across lists, "found by both
    ranks highest", **hybrid beats vector-only** on a fixture where a lexically-
    exact identifier is buried in the vector ranking, config validation.
  - `SearchControllerTest` — authorization gate (403 when caller can't read the
    org), result mapping, snippet truncation (mocked collaborators; no web stack).
  - `PgVectorChunkStoreTest` — vector-literal formatting (from M4).
- **Authored, CI-only (Docker):** `HybridSearchIT` — real pgvector + Postgres FTS:
  upsert chunks via the M4 store, search, assert file:line provenance and
  org-scoping against a live container.
